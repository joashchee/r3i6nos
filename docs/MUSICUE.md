# MusiCue: Cue on the R36S (2026-11-19)

**Status: a first slice is built (`apps/musicue-native/`), tested in Debian 12 arm64 under Docker and on a Mac, and never run on a real R36S.** What is and is not done is in "What is built" and in
ROADMAP section 36. MusiCue is the R36S port of the maintainer's web app Cue (`~/Coding/cue`, https://cue.chordica.com/: jump markers and synced captions on a YouTube video, A/B loops, Set Lists), rebuilt
around **an audio file on the card** and working **offline** once the device has fetched what it needs.

## Decisions (the maintainer, 2026-11-19)

| Decision | |
|---|---|
| **Local files, plus a yt-dlp add-on** | The sound is a file the person has. A separate, optional sync fetches Cue's server cue files and, with the yt-dlp package installed, audio |
| **Rebranded MusiCue** | The port has its own name. It is not a YouTube API client, so Cue's terms and privacy pages do not describe it (a text of its own is still to write) |
| **No video**, only **an audio waveform at the top showing the whole song (no scrolling) and a moving playhead** | Rows 1-6 are pixels; the rest of the screen is cells |
| **Everything else is the r3i6nos-ansiapps text mode, in true colour**, with gradients and shades | Palette slots 32-255 hold gradients made from the chosen theme; every text pair still passes 4.5:1 |

Cue's own rules had to be weighed (its `CLAUDE.md` rule 1, strictly a web app, and rule 3, no downloading or caching video, kept from the YouTube API review): a native port is a different thing, and the
yt-dlp add-on is what leaves rule 3. **One default was chosen to keep the add-on inside the line the maintainer has drawn so far: it fetches Creative Commons videos only** (yt-dlp's `license` field,
`--match-filter "license*=Creative Commons"`; the field's exact text should be checked against a real video), and fetching any video is a setting, off, in Start > Fetch from YouTube. **Also save the video (480p)** (a checkbox under it, off, 2026-11-20) makes `musicue-sync --video` download the picture into `video/` after the audio: H.264 (avc1) + AAC in an mp4, at most 480p and 30 fps, as `docs/VIDEO-DECODE.md` and `docs/STREAM-TOOLS.md` settle (the screen is 640x480; the VPU has no VP9 or AV1 and software decodes; 720p is wasted pixels); format 18 (360p) is the fallback and the battery option. **Whether the unit decodes 480p in real time is not measured (ROADMAP section 35 step 1); if it does not, lower the cap to 360p in `VIDEO_FORMAT`.** Untested on a unit. That default is
a recommendation to confirm or change; it is not legal advice, and what a person fetches is theirs to answer for.

### How it works, and why

- **The song lives in RAM.** 44.1 kHz stereo 16-bit is 176 KB/s: **4 minutes is 42 MB, 12 minutes (the cap) 121 MiB**, on a unit with about 848 MB free with an app running. A jump is a pointer move and the loop
  wraps inside the buffer the audio callback is filling, so it has no gap (a test checks the callback's samples across the wrap, sample for sample). Opening costs one decode: a WAV is read here, anything else is
  one `ffmpeg` run on a pipe (AAC decoded 19 s of audio in 0.01 s on a Mac; the unit's time is untested).
- **The waveform is the only pixel drawing.** 640 columns, one per pixel, each the lowest, highest and RMS of its slice of the song; long songs are sampled inside a column (a 12-minute track took 13 ms on a Mac, and one
  redraw 1 ms, neither measured on the unit). It redraws only when the playhead moves a pixel (a 4-minute song: under three times a second), a marker changes or the palette does. The pixel columns line up with the
  64 text columns (ten to one), so the section strip and the marker names under it are in step with the picture.
- **True colour in a cell grid.** A cell holds a palette slot, so gradients are palette ramps: a bar ramp (the top bar), an accent ramp (the selected row, the cue playing now, the progress bar), 32 marker hues
  (bright for played, dim for to come), and a text-to-page fade whose every step is chosen to keep 4.6:1 against the page (the cues before and after the current one fade along it). A cell on a gradient takes black
  or white by contrast, which is always at least 4.58:1. The marker colour comes from the marker's name with its number removed, so every "Chorus" has one colour and a song's structure reads at a glance.
- **Cue's rules are in the code.** The metadata fields cannot be added to by any file; a value is cut to its limit on a character boundary; `created` is dropped unless it looks like an ISO time and is only ever set by an
  export; the 33 marker key slots (1-9, 0, d-z) are assigned in time order for the files Cue reads. An import that disagrees with a file already there goes to `cues/.merge-conflicts/`, never over it.
- **The sync never overwrites a person's work, sends nothing but its requests, and is the only online step** (rule 6). It reads `inbox/urls.txt`, fetches each video's server cue files if the server has any (most videos
  have none), and, if yt-dlp is installed and the video is Creative Commons, its AAC audio (about 1 MB a minute) into `media/` as `Title [id].m4a`, which is how the app matches a file to Cue's data.

## The pad, the panels and Tempo (2026-11-19, maintainer's map)

**Buttons (the map of 2026-11-20, replacing the first one of 2026-11-19; the full table is in `apps/musicue-native/README.md`, "The pad"):** MusiCue follows `docs/r3i6nos-mapping.md` through `theme/r3i6nos_input.h` and `theme/r3i6nos_mainmenu.h`:
**L1+R1 the main menu** (About, Colour theme, Device report, Rec demo, Quit, then Songs and sync or Song options; Benchmark hidden), **L2+R2 or Y the context menu**, **Fn the next panel, L1+Fn the first, R1+Fn the one before**, the right stick through the reader's dead zone and rate,
R1 held for pages and Home/End. **Start plays (Play mode); L1+Start plays in Rec mode; playing, Start stops and ends Rec mode.** **Rec mode:** D-pad Down adds a cue, Up takes the last cue of the take back, Left and Right go to the cue before and after.
**Play mode:** Up and Down go to the first and last cue, Left and Right to the cue before and after. **R1+Up/Down set A and B, R1+Start switches the A-B loop (A and B are kept), R1+Select goes to A.** Select alone is 0:00. L1, R1, L2 and R2 alone do nothing, and the old
L1/R1 marker steps, L2/R2 10 s and Y loop cycle are gone (R1+Left/Right is 10 s). Quit is in the main menu and Select+Start no longer leaves. Markers have no button: a marker is a bookmarked cue (the context menu).
**Panels (rows 9-20, two at a time, Fn turns the carousel one place, and a seventh place is the Jump panel on the whole width, the one with the stick has the double frame):** Markers, Cues (time, a tempo dot, a marker flag, the words), Metadata (key, tempo, sig, scripter, created; A edits, Sig toggles 4/4 and 6/8,
a number or a letter picker for the rest, a USB keyboard types), Set List, **Last 10 cued**, **Top 10 cued**.
**Set List** is Cue's: an ordered list of songs (add this song, move up and down, remove, A opens), in `setlist.tsv`. **Last and Top 10 cued are local**: Cue's are server lists across all users (its `VIDEO_LOG_ENDPOINT`, not deployed), which MusiCue
cannot have under rule 6 (no telemetry), so these are the songs *opened on this unit* (`history.tsv`: newest first; most opened first). Cue's versions of a song are not in MusiCue yet, so a Set List entry is a song and not a song-and-version.
**Tempo is Cue's logic, read from its source** (`computeGapTempo`, `classifyTempoDot`, `computeSuggestedTempoCluster`, `maybeSuggestTempo`, `renderCaptions`): a cue's length (its start to the next cue's start) is 16 beats in 4/4, 8 in 6/8 (any other Sig counts as 4/4, and MusiCue says so),
so it has its own tempo, `60 / (length / beats)`; against the Tempo it is **green within 2 BPM, yellow within 5, red beyond** (the last cue has no dot). A Tempo that is blank or `?` is **suggested**: the largest group of cues within 2 BPM of one of them (the first found on a tie), averaged to two
decimals, those cues green. It runs when a cue is added or deleted, when a song with cues opens and when the Sig changes, and **never overwrites a Tempo that was typed**; Metadata > Tempo with the number erased, or the menu's Recalculate, asks for it again. As in Cue, once suggested it
is a number like any other, so later cues do not move it until it is erased. The Assisted Cue entry's bars use the green cues only.

## The Jump panel, the Piano and numbered marker names (2026-11-20, maintainer's request)

**Jump panel** (rows 9-20, the whole width; the carousel's seventh place): every marker, a page at a time, with **Cue's playback-progress fill** (`updateMarkerProgressFills` in Cue's source): the marker's own section, from its time to the next
marker's, fills left to right in the marker's colour while the playhead is in it, one section at a time, and **the last marker has no section** (Cue's rule: no next marker to bound it), so it never fills. A triangle marks the marker last passed, an `L` the sections inside a running A-B
loop. The bottom row is **Cue's A-B progress** (`updateTempLoopCProgress`): A, a bar, B, filling only while the loop is on (empty when it is off or B is not set yet). The **eight buttons** (D-pad up, down, left, right, then A, B, X, Y) are **one-touch**:
the right stick picks a marker, **stopped** a press binds it (again on the same marker frees it), **playing** a press moves the playhead there; each row shows the tags of its buttons. Bindings are kept by the marker's time in `cues/<id>.jump`. R1+Up/Down/Start/Select
keep their A-B meaning there. The Jump panel overrides Rec mode's D-pad (record on another panel). **Fn while Play mode plays goes straight to the Jump panel, wherever the carousel is; when the music stops, the panels that were showing come back** (a manual Fn or L1/R1+Fn in between cancels the restore; Rec mode does not do this). **Not decided by the request, so chosen here:** the Jump panel is the last place of the carousel (after Top 10 cued); B does not leave the song on it (a face button is a jump button).

**Piano.** Editing the **Key** in Metadata opens a floating Piano panel (the field's box shrinks to the upper half): one octave, **C3 to B3** (C3 is 130.81 Hz, scientific naming), played through the same audio callback over the song (a sine with two overtones and a decay, up to 12 voices, a released note fades in 50 ms), so a person finds the
key by ear while the song plays. D-pad Up C3, Left D3, Down E3, Right F3; Y G3, B A3, A B3, X A#3; L1 C#3, L2 D#3, R2 F#3, R1 G#3 (shoulders are notes there, not modifiers, so L1+R1 together is two notes and not the menu); **Select Oct-, Start Oct+** (octaves 1-5); **Fn closes it**
(and opens it again). **A note writes the key's root** (sharps: C#, not Db) and keeps what follows it, so Am7 played G is Gm7; A keeps the key once the piano is closed (A is B3 while it is open), B cancels. Tested for the notes, the voices (no clipping) and every theme's contrast; **never heard on a unit.**

**Numbered names.** In "Name the selected marker", **Right on a preset** (Intro, Verse, Pre-Chorus, Chorus ...) asks for a **number or letter after it**: Up and Down walk 1-9, A-Z, a-z, 0; Right moves to a next place (so Verse A, Chorus 1a); A keeps "Verse 1a", B cancels; A on the preset alone keeps the plain name.

**What this changed:** Device report and Rec demo in the main menu say they are not built yet (Rec demo is the video of rule 11, nothing to do with Rec mode); the old Theme menu item is the main menu's Colour theme; the old menu's items are now Songs and sync (Add, Sync, Import, Demo song, Fetch from YouTube)
and Song options (Offset, Save, Export, Add to the Set List, Recalculate tempo, Back to the songs); the context menu has Cue here, Mark here and what the focused panel can do. **Untested on a unit:** every press (the pad, the shoulders as notes, the chord feel), the piano's sound and latency.

## The cue panel (2026-11-19)

Rows 7 and 8, under the waveform, are Cue's cue panel (the section strip and the playhead triangle are gone; the loop and the offset moved to the command line's status). **Row 7: the cue playing now** (its start has passed and its end has not; a cue with no end runs to the next cue, the last one 6 s), with the **beat dot** at the right, a green dot that pulses once a beat (from the Tempo, anchored to the start of the cue playing, only while the song plays). **Row 8: the next cue, muted**, only while a cue is playing. **At the last cue, row 8 is Cue's Assisted Cue entry instead**: two bars, full at the last cue's start, draining toward the middle over the average length of the cues whose own tempo is green (within 2 BPM of the Tempo; 16 beats a cue in 4/4, 8 in 6/8), shown only when the Tempo is set, the song plays and there is room for one more cue, as Cue's `updateAssist()` decides. MusiCue had no way to make a cue, so **D-pad Down** (and the menu's Cue here) stamps one at the playhead, reading "- - - -" as in Cue; the words are still typed in Cue. Tested in `--selftest` (`test_cue_panel`); **not looked at on a unit**.

## Add: YouTube ID (2026-11-19)

The menu's (L1+R1) **Add: YouTube ID (11 chars)** opens an 11-slot entry with an on-screen keyboard: a 16 by 4 grid of A-Z a-z 0-9 - _ (D-pad moves and wraps, R1 held jumps to the top or bottom row, A types the key and moves on, X or Y erases, Start fetches, B cancels; a USB keyboard types it too; case matters). The keyboard is local to this entry, not the theme's shared one (mapping doc, "The virtual keyboard", not built yet).
A on the last filled slot, or Start, goes. **Online** (a default route in `/proc/net/route`; nothing is sent to find out) it runs `musicue-sync --id <id>`, which does what Sync does for that one video, and when it ends
the song opens. **Offline** the id is appended to `inbox/urls.txt`, so the next Sync gets it. **The Creative Commons default still applies:** a video that is not CC gets its cues (if the server has any) but no audio, and the job
screen says so; Start > Fetch from YouTube lifts it. Tested against a fake helper (`--selftest`) and `tests/test_musicue_sync.py`; **untested on a unit and with real yt-dlp over Wi-Fi.**

## Key and Tempo: render a copy (2026-11-20, maintainer's idea; ROADMAP section 40)

**Built (2026-11-20): the renderer (`tools/stretch-proto/`), its streaming helper `musicue-render` and the app's screen and job; tested on a Mac and in Debian 12 arm64; **first run on the unit and listened to on 2026-11-20 (one song, below)**.** Practice speed and transposing are done **offline, not live**: a song with a declared Key and Tempo (Metadata, the song's base values) can be asked for another Key and/or Tempo, and on a confirmation the app renders **a copy** of the song at the new values on all four cores. The copy is an ordinary song: playback is the unchanged 1.0x engine, so **instant marker jumps and gapless A/B loops keep working** and there is no ring buffer, no latency to correct and nothing to run in the sound callback. (A live stretcher was the first idea and was dropped: it needs a worker thread, a ring buffer, a flush on every jump and the loop wrap fed through it. The research behind this is `docs/r36s-audio-processing-reference-kit.md`.)

**The numbers.** `ratio = target Tempo / base Tempo` (2 is twice as fast and half as long); `semitones` = the distance from the base Key to the target Key, in the nearer direction (at most 6, up or down), **keeping the mode** (major stays major, minor stays minor: G major to A major is +2). A song with no Key or no Tempo cannot be rendered: the item says which is missing and sends the person to Metadata. Signalsmith Stretch sounds best at **0.75 to 1.5 times** the speed (its README) and takes several octaves of pitch, so the screen allows ratio 0.5 to 2 and warns outside 0.75 to 1.5.

**The engine: Signalsmith Stretch** (MIT, header-only C++11; with Signalsmith Linear for the FFT, also MIT), one instance per thread, **because the library is single-threaded**. Rubber Band is GPL (or a paid licence), so it is not linked: if the R3 "finer" engine's quality turns out to be worth its CPU, it would be an optional package run as a separate program, one copy in the image like `ffmpeg` (rule 15's idea). SoundTouch's WSOLA smears polyphonic music.

**How it uses the cores** (`tools/stretch-proto/stretch_render.hpp`):
1. **Cut the song** into segments of about 20 s, at least as many as workers, **each cut moved to the quietest 50 ms within a second of its even place** (never nearer than 2 s to the last cut).
2. **Render each segment on its own thread**, with **1 s more of the song each side** so the phase vocoder settles before the part that is kept (`exact()`, a fixed seed per segment: the same input gives the same bytes whatever order the threads finish in).
3. **Join with a 50 ms linear crossfade at each cut, after aligning the pieces.** Two independent phase vocoders agree on the notes but not on the phase: without alignment a steady tone **dipped to 0.07 of its level at a cut** (found by the first run). Each piece is moved by up to **15 ms** to the lag where it correlates best with the piece before it over 80 ms (the smallest shift among the nearly-best wins; the shift is absolute, never added to the last one, so **no sound is ever more than 15 ms from where the new tempo puts it**). With the pieces aligned a linear fade is right; **an equal-power fade swelled the cut to 1.31 times** (the first run again).
4. A song of 4 minutes: 4 MiB of working memory per instance plus the output; the prototype holds every piece in RAM, **the app's version will write each piece to the output file as it finishes** (and so resume after a power cut, below).

**Cues and markers move with the sound.** Every time in the copy's cue file is the base song's time **divided by the ratio** (plus the same offset), and its Tempo field is the target; the Key field is the target Key. The copy keeps a pointer to the base (`base=<id>`, `ratio`, `semitones`) so the library can group them and so a cue edit can be offered back. Names: the library shows "Song (G, 96 bpm)".

**The job screen** is the fetch job's: a determinate bar (segments done of segments), the estimate, B cancels (a half-written copy is deleted). **Before it starts, a confirmation says**: the base and target values, the ratio and the shift, **the estimated time** (the song's length / (speed of one worker on this unit, from the Device report's `== stretch ==` section x workers x 0.85)), the free space on the data card (the copy is about 10 MiB a minute), the battery, and **2 workers or 4** (4 is fastest and warmest). It **refuses below 20% charge** unless the charger is in, as rule 16's move does. Everything else is locked while it runs, like Rec demo (rule 11). One copy per (song, key, tempo); the data card's `MusiCue/` folder keeps at most a set number and offers to delete the oldest.

**Rules to meet when it is built.** The **Device report** gets `== stretch ==` (rule 9): one worker's speed against real time on a fixed 30 s clip, then 1, 2, 3 and 4 workers (how it scales on four Cortex-A35s sharing one memory bus), the copy's length and pitch checked, and the peak memory; **`== power ==`** (rule 14) gets the render as the "working" state with the draw in mW and the temperature if the unit shows one, with a goal and a FAIL line. **Rec demo** (rule 11) renders a short copy of the demo song. The self-test covers the Key and Tempo arithmetic (the nearer direction, the mode kept, the cue times), the file naming and the cancel; **all of it untested on a unit.**

**What the prototype shows so far** (Debian 12 arm64 under Docker, an Apple core, **not a Cortex-A35**): a 40 s sine through ratios 0.75, 1.0, 1.25, 1.5 and shifts of -2 and +3 semitones comes out the right length (to the frame), in tune (within 0.2%), with no click and no level dip at any of the three cuts; a 60 s synthetic song gives the same bytes on a second run and its level matches the one-piece render's within 1% in every half second. 60 s of audio took **0.81 s on one worker and 0.26 s on four** (3.1 times faster, 227 times real time) on that core; **an A35 is several times slower and shares one memory bus, so these say how it scales and nothing about the unit: the unit's number is the Device report's.**

**Measured on the unit (2026-11-20, first report; ROADMAP section 40 step 2):** four Cortex-A35 at 1512 MHz. 60 s of audio at ratio 0.8 and +3 semitones: **one worker 3.4x real time, four workers 9.3x** (2.7x faster than one); with `presetCheaper` **5.4x and 13.8x**. So **a 4-minute song's copy takes about 26 s (17 s cheaper) and a 10-minute one about 65 s (43 s)**. PFFFT's NEON FFT gains only 5-10%, so the built-in FFT stays. The self-test (length, pitch, no click, no dip, same bytes) passes on the unit. **The prototype used 119-127 MB for 60 s of audio, so the app must write each piece as it finishes and keep only the segments in flight** (a 10-minute song would be over a gigabyte in the prototype). The unit warmed from 39 to 54 C and held 1512 MHz. About 0.6 W more than idle while rendering (a rough figure; the first report's power section had a sign error, fixed). **First listening test (2026-11-20, the maintainer's, one real song, an m4a):** the copy rendered on the unit after two fixes (the ffmpeg `wav` muxer, then clipping). The job reported `limited a 1.80 peak: ducked 10.7% of the time, deepest -5.2 dB`, so the stretcher overshot a loud master by about 5 dB; **on earphones the copy sounded good with no distracting artefacts**, and the earlier clipped version had also sounded fine on the R36S's own speaker (which hides clipping, so the limiter stays). **One song only:** no vocals-led, quiet, sparse or very dense material yet, no big shifts (a few semitones, a few percent of tempo), and the cues against the copy and jumps and loops on it were not reported.

**Second report, and where the time goes** (four workers, 60 s of audio, default preset, 6.43 s): 4.1 s is the work divided by four, 0.9 s is the four cores slowing each other (the same work takes 23% longer in total on four cores than on one: the shared cache and memory bus), 1.0 s was the serial join (now made about twice as fast: it reads the alignment window from contiguous arrays and mixes the body of each piece with plain adds), and 0.4 s is imbalance and start. Three workers (7.25x) are not worth offering beside 2 (6.26x) and 4 (9.33x). The app's estimate should use the measured 4-worker speed less a margin, and show the song's length over it.

**As built (step 3).** *The screen:* Song options (L1+R1 > MusiCue's own item, or the player's options) > **Key and Tempo: make a copy**. It starts from the song's own Key and Tempo fields (a missing one, or a Key that is not a note, is refused with what to fix; a copy cannot be copied). Left/Right moves the target Key a semitone (the mode is kept; the shift goes the nearer way round, -5 to +6), Up/Down the Tempo 1 bpm, **R1+Up/Down 5 bpm**, **R1+Left** puts back the song's own, **X** 2 or 4 workers, **Y** best or faster (`presetCheaper`), **A** makes it, **B** goes back. It shows the shift, the speed ratio (allowed 0.5 to 2; a warning outside 0.75 to 1.5), the estimate (`kt_estimate_s`: the song's length over the speed the unit measured, 9.33x for 4 workers and 6.26x for 2 with the best preset, 13.3x and 9.15x with the faster one, plus 25% and 2 s) and the copy's size. *Before it starts:* under 20% battery off the charger, or less room than the copy needs (plus 5% and 16 MiB), is refused with the reason; if the same copy is already there it is selected instead. *The job:* the song is saved and closed, `musicue-render` runs on the job screen (a determinate bar of segments joined, B stops it and removes the part and the journal; leaving the app instead keeps them, and asking for the same copy again continues it). *The copy:* a WAV `media/Title (A 104bpm) [kt-xxxxxxxx].wav` (the id is `kt-` and eight hex digits of the base id, the shift and the ratio, so it is stable; the base's own " [id]" is dropped from the title), a cue file made from the base's saved cues (**every marker, cue start and end divided by the ratio**, Key and Tempo set to the target), `.offset` divided by the ratio, and `cues/<id>.kt` (`base=`, `ratio=`, `semitones=`, `key=`, `tempo=`). Cue files keep times to the millisecond, so the copy's are rounded there.

*`musicue-render`* (`tools/stretch-proto/musicue_render.cpp`, `stream_render.hpp`; `musicue-render --in SONG --out COPY.wav --ratio R --semitones S [--workers N] [--cheaper] [--no-resume]`): a 16-bit 44.1 kHz stereo WAV is read directly, anything else through the image's `ffmpeg` **as raw `s16le` on a pipe, as the app's own decoder does it** (the image's ffmpeg has no `wav` muxer: the first unit try asked for one and failed with "output format 'wav' is not a suitable output format"), a song over 12 minutes (the app's own limit) refused rather than cut; segments of about 20 s (at least 4 for a song of 16 s or more) are rendered by up to 4 workers, never more than workers + 1 ahead of the join; pieces are joined in order into a small window (the same alignment and linear crossfade as the prototype) and written to `COPY.wav.part`; **after each flush a journal** (`COPY.wav.journal`: the song's length, ratio, shift, preset, segment count, how many are joined, the frames written, every alignment shift) is written atomically after an `fsync`. **Resume** truncates the part to the journalled length, re-renders the two segments around the last cut and goes on. Because the plan depends on the song only and every segment has a fixed seed, **the same bytes come out with 1 or 4 workers and after a resume** (checked by `test-render.sh`, with a power cut simulated after the first and second checkpoints and a real SIGTERM). A 400 s song peaked at 179 MiB. **A limiter** (found by the first listening test, which reported clipped samples; the second said a 1.80 peak): a phase vocoder overshoots at transients, and a loud master has no room. Every piece goes through a lookahead limiter with a ceiling of 0.985: the gain starts to fall 1.5 ms before a peak and holds 1.5 ms after, and each frame's gain is at most what brings it to the ceiling. **The release depends on the program**: after a brief spike (under 30 ms of asking for a duck since the gain was last at rest) it comes back in 40 ms for a full swing, so a lone peak costs a short dip, not a hundred milliseconds of pumping; while the music keeps asking, it comes back in 300 ms, so a loud passage does not pump either. It is done per piece on the whole piece so it needs no state across pieces (the same bytes for any worker count and after a resume, tested). A piece that never reaches the ceiling is not touched at all. The `DONE` line says `limited a 1.80 peak: ducked 4.2% of the time, deepest -5.1 dB;` when it worked (the loudest sample before the limiter, how much of the copy was pulled down by more than 0.1 dB, and the deepest gain), `N samples clipped;` only if something still got through. Exit 0 done; 1 an `ERROR` line; 2 usage; 130 cancelled. The package carries it as `usr/lib/musicue/musicue-render` (built by `scripts/build_native_app.sh` when `app.conf` has `RENDER_HELPER=1`).

**Open:** a limit on how many copies are kept (and an offer to delete the oldest); offering the half copy of a power cut at start; "copy of" shown in the library (today the name and sort order are the link); the Device report's `== stretch ==`, the power section and the Rec demo (ROADMAP section 40 step 4); listening to real music (step 5); everything on a unit.

**Stems.** The same job machinery runs one render per stem (stems x segments, four workers draining the queue). Splitting a song into stems is not done on the unit (Demucs needs PyTorch and more RAM than the unit has; the options, with a computer-side script, a centre-channel cancel, a bass crossover and an HPSS drums/rest job, are a later step, ROADMAP section 40 step 6).
